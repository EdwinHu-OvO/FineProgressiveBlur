# Massive Blur Dashboard

打开 `/massiveblur`，或从首页进入「大面积模糊 Dashboard」。页面使用必应每日一图作为固定背景，十张可交互卡片组成原生可滚动的工作区。工作时长、项目和日程明确标为示例；待办、专注计时、项目筛选和随手记可操作。

## 渲染结构

一个固定于视口、设置 `sourceMode="static"` 的 `GradientBlurProvider` 缓存整张背景。每张可见卡片有自己的 `GradientBlurOverlay`，均不传 `direction` / `mask`；Provider 内部按半径共享单块降采样图集和已完成的模糊结果。Provider 内只有图片采集源和直接子级 Overlay；清晰的前景 DOM 独立位于其上，因此输入、文字变化和计时更新不会混入背景采集。

`useCardRegions` 合并窗口滚动和尺寸变化，在动画帧里读取可见卡片矩形；`GlassBackdrop` 更新各 Overlay 的位置和 Provider 外部的圆角裁剪路径。组件把位置变化作为局部合成请求，后续 Overlay 直接裁切共享纹理，无需重新采集、构建降采样金字塔或卷积。图集保留完整背景邻域，圆角不作为强度蒙版参与切分。DOM 矩形跟踪属于演示页，静态源与共享结果是通用组件能力。

默认半径 48px，可调整到 0–96px。关闭模糊将半径归零，保留组件的原分辨率采样路径作外观对照，并不表示停用整个 WebGL 后端。尺寸、半径、后端切换沿用现有更新机制；两种采集后端均复用同一张背景。背景固定不动，卡片随窗口原生滚动移动。

这种复用适用于同一背景版本和同一半径。背景图片的 `onLoad` 调用 Provider 的 `refresh()`，显式通知新图片就绪；视口大小和 DPR 改变会重建背景。半径变化只更新对应模糊结果，不重新上传背景。完整语义见 [静态背景 API](static-source.md)。

## 滚动 GPU 排查

初版为每张可见卡片创建 Overlay，滚动时写入其 `top` / `left`。位置观察器将变化传给 `surface.request("resize")`，触发全部 Overlay 重建采样图集；`uploadGpuAtlas()` 又清空卷积缓存。各卡片的采样邻域还互相重叠，因此即使 Rito 已缓存背景、不再上传 Canvas，GPU 仍反复执行编码拷贝、降采样和卷积。卡片进入/离开视口时还会创建/销毁 renderer。

Apple M4 / ANGLE Metal、1440×1000 CSS px、DPR 2、48px 半径，预热后连续滚动约 1056px / 3 秒的调用计数：

| 后端           | 原绘制次数 | 原 framebuffer 拷贝次数 | Provider 共享后的合成绘制 | 共享后的拷贝 / 卷积 |
| -------------- | ---------: | ----------------------: | ------------------------: | ------------------: |
| Rito           |      9,369 |                   2,904 |                     1,451 |               0 / 0 |
| HTML-in-Canvas |      9,442 |                   2,943 |                     1,451 |               0 / 0 |

两种后端在这段滚动中均没有新增背景上传、编码、高斯、framebuffer 拷贝或纹理分配。多个 Overlay 的裁切合成仍会绘制。前后都接近 60 FPS，所以单看帧率或源纹理上传次数不能发现原问题。这些是 WebGL 调用计数，不是整机 GPU 占用百分比；浏览器的裁剪、光栅化与滚动合成仍有成本。

之前的页面专用实验使用单个全屏 Overlay 加外部裁剪，滚动时可以没有新增 WebGL 绘制；本版本改为多个独立 Overlay，验证 Provider 的通用共享能力。旧实验数据保留在原 Dashboard 验证文件，当前数据见 [静态 Provider 验证](benchmarks/static-source-2026-09-10.json)。

## 背景获取

- `/api/bing-wallpaper` 读取 Bing 的 `HPImageArchive.aspx`，使用 `zh-CN` 市场，服务器每小时重验，浏览器缓存 5 分钟。
- `/api/bing-wallpaper/image` 只接受受限的 `OHR.*` 图片 ID，从固定 Bing 主机读取 1920×1080 图片，转换为同源响应，供 Canvas / WebGL 安全采样。不是任意 URL 代理。
- 客户端解码完成后一起切换原生背景、采集源和缩略图。显示 Bing 返回的标题、日期和摄影版权信息。
- 请求超时、图片解码失败或网络不可用时保留仓库已有的本地照片，并标明临时预览状态；其署名见 [图片说明](../public/images/ATTRIBUTION.md)。不把旧的本地照片标为当日 Bing 影像。

GitHub Pages 不提供运行时接口：`build:pages` 在构建前下载匹配的元数据和图片，生成 `/wallpaper/bing-wallpaper.json` 与带图片 ID 的同源图片文件。静态版读取这份快照，壁纸随部署更新；任一下载失败则导出本地照片的元数据。动态接口以 `route.server.ts` 命名，仅服务器构建启用。图片、蒙版、署名和请求路径均遵循 `NEXT_PUBLIC_BASE_PATH`。

## 性能读数

首屏提供半径控制、当前后端、可见卡片面积与滚动帧率；滚动后的小型浮窗保留最新帧率，并提供返回控制区的入口。「采样与性能详情」展开后可切换后端与最大 DPR，查看采样率、共享图集大小、采集块数、最近一次 JS 提交时间和滚动帧间隔 P95。

帧率由滚动期间的 `requestAnimationFrame` 间隔计算，空闲时停止采样，并明确标记「上次滚动」。它包含页面、浏览器、布局与合成成本，不是独立的 GPU 卷积计时。面积为可见卡片矩形的估算。图集指标只计当前共享项，不把各卡片重复相加，也不包含背景、金字塔、卷积中间缓冲和闲置历史；背景原图指标为整个视口的 RGBA 采样尺寸。JS 提交时间使用共享项最近的布局和上传数据，不能当作 GPU 完成时间。

页面样式表和性能区样式表集中维护各自的布局、交互状态和响应式规则，属于同一责任的声明式样式；其余业务模块均控制在 200 行以内。

## 验证

2026-09-10：lint / typecheck 及 19 个测试文件、81 项测试通过。浏览器检查覆盖：

- Apple M4 / Chromium 153 / ANGLE Metal，Rito 和启用实验 flag 的 HTML-in-Canvas。
- 一个 Provider / 一个呈现 Canvas / 多个可见 Overlay，相同 `sharedTexture` 标识确认复用，卡片矩形与 Overlay 一致。
- DPR 2、96px 半径时采用 1/64 采样；归零恢复 1×。
- 两种后端连续滚动期间只有裁切合成，没有新增高斯绘制、framebuffer 拷贝、纹理分配或背景上传；半径与尺寸变化仍重建共享结果。
- 计时暂停/重置、任务完成度、项目筛选和文本输入。
- 390px 窄屏无横向溢出，滚动后卡片与裁剪区域继续对齐。
- 禁用 WebGL2、Bing 请求失败时每个 Overlay 使用单层 CSS 模糊和本地图像。

本地开发模式的短时测量用于验证这次实现，不承诺其他设备或所有页面内容的固定帧率。测量记录见 [Dashboard 验证数据](benchmarks/massive-blur-2026-09-10.json)。
